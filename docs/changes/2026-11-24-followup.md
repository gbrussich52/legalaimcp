# 2026-11-24 follow-up: two paid tabs

Closes the two-tab item in the "Still open" paragraph of `2026-11-22-intake.md`.

## What changed

`app/api/stripe/webhook/route.ts`: a paid checkout for a listing that already holds an active paid term, bought by a different payment, no longer changes the row. The handler logs one line, `PAID_NO_PLACEMENT session=<id> listing=<id> reason=active_term`, with `console.error`, and still answers 200.

The guard is part of the listing UPDATE filter, so it is atomic. The filter is still one `.or()` value. It now holds 12 `and(...)` terms: (not newer) x (not editorial) x (no end date, or end date past, or this payment holds the term).

"Same payment" is equality of `featured_purchased_at` with this payment's `purchasedAt`. `purchasedAt` is the `created_at` of the payment's `listing_payments` row. The listing row also has `stripe_checkout_session_id`, but a newer purchase overwrites it, so the timestamp is the stable key. No column or migration was added.

## What the code did before

Two sessions opened before either was paid could both be paid. The second payment restarted the 30 days, so the vendor paid twice for about one term. If the older payment was applied second, the update matched no row, the code read the row, saw a newer purchase, and returned with no log line.

## Tests

`app/api/stripe/webhook/route.test.ts`: both arrival orders (A then B, B then A), redelivery of the paying session, and a purchase after the term ended (also when the cron has not cleared `featured`). The filter test now expects 12 terms.

One earlier test changed: "a distinct purchase resets the term" bought the second term inside the first. That is now blocked, so the test buys it after the first term ends.

## Still open

The log line has no alert yet, and nothing refunds or tells the vendor. The intake watcher check for a paid session with no matching placement is still planned.

## Second pass: review fixes

Changes in `app/api/stripe/webhook/route.ts`, tests in `route.test.ts`.

- Same payment is now the Stripe session id. Before, it was equality of `featured_purchased_at` with this payment's time. JavaScript reads times to the millisecond and Postgres keeps microseconds, so two payments could look like one. The third filter factor is now `stripe_checkout_session_id.eq.<session id>`. The readback after a zero-row update compares `stripe_checkout_session_id` with this session. A session id that is not letters, digits and underscores is refused before the filter is built, because it goes into the filter string.
- One clock reading per event. The filter's `featured_until.lte.` term and the readback's "is the term still active" test use the same `now`. Before, a term that ended between the two calls was read differently: the older payment fell through to "Featured applied" and the newer one threw.
- A no-placement decision stays decided. On both `PAID_NO_PLACEMENT` branches (`editorial_pick`, `active_term`) the payment's `listing_payments` row is set to `no_placement`. At the start of the apply step, a session whose ledger row has that status returns 200 with an info line and the listing is untouched. Before, a resend after the other term ended placed the payment with whatever was left of its own 30 days. `listing_payments.status` is free TEXT (migration 007), so no migration. If the status write fails, the route logs `NO_PLACEMENT_STATUS_NOT_SAVED session=<id>` and still answers 200, so Stripe does not retry and the line is not doubled.
- Not changed: clock skew between the web server and the database.

- `docs/catalog-review.md`: the realness step and the `operator` field.

### What the code did before

Nothing checked that a vendor exists. The gate compared claims with vendor pages, and `curate.mjs` only classed link status. A made-up vendor with a convincing site could pass every check.

### Why

The owner's rule is zero trust. A vendor's pages prove what the vendor says. Registry dates, DNS and a live MCP handshake come from parties the vendor does not control.

### Limits

The checks show what was observed on a date. Registry presence confirms control of a namespace, not quality. `operator` is a person's finding in a company register; the code checks only that it is complete.

## Third pass: the checker on hostile addresses

Claude Sonnet 5.5, 2026-11-23.

### What changed

`scripts/realness.mjs`, tests in `lib/realness-safety.test.ts` (25 tests, offline, resolver and fetch injected through `setDeps`).

- `screenUrl` is a pure address test: https only (an http input is upgraded to https before the first request; an http redirect hop is refused), no login part, no IP host, no local name, a public suffix and a registrable domain (`tldts`).
- `isPrivateAddress` expands IPv6 to eight groups. Before, `::ffff:7f00:1`, `::ffff:c0a8:101`, `::127.0.0.1`, `64:ff9b::7f00:1` and 6to4 forms of private addresses all passed as public.
- `safeFetch` screens and resolves the host on the first URL and on every redirect hop. A refused address throws a `private` error. It also refuses any POST body that is not `initialize` or `server/discover`.
- A refused address is a `site` fail with "The address is not a public web address." and no other probe runs.
- `--submission FILE` for raw submissions. `--plan` accepts a bare name and URL, but collides on same-name submissions and has no submission id.

### What the code did before

It already allowed https only, refused a login part and IP literals, resolved the host through DNS over HTTPS (system resolver only as a fallback), followed redirects by hand (5 max, host test on each hop), capped bodies at 2 MB and timed out at 15 s. It did not check the public suffix or local names, trusted DoH alone (the machine's own resolver was not compared), missed the hex forms of mapped addresses, turned a refusal into `unknown`, and did not limit POST bodies in code.

### Still open

DNS rebinding between the check and the request is not pinned, but https only blunts it: the connection resolves the name again, and a rebound answer has no certificate for the name, so the handshake fails before anything is sent.

### What the code did before

No review carried an operator, so every listing page printed "We have not yet looked this operator up in a company register."

### Why

A vendor's own pages prove what the vendor says, not that the vendor exists. A register entry is evidence the vendor does not control. Each record here was read twice: by two separate readers, or by one reader and a second read of the official record.

### Limits

- vaquill-ai rests on two public mirrors of India's register. The official register needs a sign-in. The record says so.

- specterai links to the tax agency's service notes, because the lookup itself is a POST request with no page to open.
- The other 58 listings have no operator record yet and still print the "not yet looked" line.
