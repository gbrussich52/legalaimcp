# 2026-11-24 follow-up: two paid tabs

Closes the two-tab item in the "Still open" paragraph of `2026-11-22-intake.md`.

## What changed

`app/api/stripe/webhook/route.ts`: a paid checkout for a listing that already holds an active paid term, bought by a different payment, no longer changes the row. The handler logs one line, `PAID_NO_PLACEMENT session=<id> listing=<id> reason=active_term`, with `console.error`, and still answers 200.

The guard is part of the listing UPDATE filter, so it is atomic. The filter is still one `.or()` value. It now holds 12 `and(...)` terms: (not newer) x (not editorial) x (no end date, or end date past, or this payment holds the term).

"Same payment" is equality of `featured_purchased_at` with this payment's `purchasedAt`. `purchasedAt` is the `created_at` of the payment's `listing_payments` row. The listing row also has `stripe_checkout_session_id`, but a newer purchase overwrites it, so the timestamp is the stable key. No column or migration was added.

## What the code did before

Two sessions opened before either was paid could both be paid. The second payment restarted the 30 days, so the vendor paid twice for about one term. If the older payment was applied second, the update matched no row, the code read the row, saw a newer purchase, and returned with no log line.

## Tests

`app/api/stripe/webhook/route.test.ts`: both arrival orders (A then B, B then A), redelivery of the paying session, and a purchase after the term ended (also when the cron has not cleared `featured`). The filter test now expects 12 terms.

One earlier test changed: "a distinct purchase resets the term" bought the second term inside the first. That is now blocked, so the test buys it after the first term ends.

## Still open

The log line has no alert yet, and nothing refunds or tells the vendor. The intake watcher check for a paid session with no matching placement is still planned.
