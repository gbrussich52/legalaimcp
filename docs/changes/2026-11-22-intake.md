# New listings from submissions, and a registry manifest fix (2026-11-22)

Claude Opus 5.5, 2026-11-22. Branch `batch/intake-2026-11-22`. Not pushed, not applied to any database.

## Why

The submit form wrote to a queue that nothing read. A vendor waited three weeks for an answer. No working path existed to publish a new listing from a submission:

- `scripts/import-reviewed-catalog.mjs` only updates rows that already exist.
- The admin Approve button calls `assertCatalogReview`, which needs the review record in the deployed `lib/catalog-reviews.json`.
- `npm run build` runs `scripts/check-catalog-artifacts.mjs` after the build. It throws when a review record's slug has no generated `/servers/<slug>` page, and that page is only generated for published rows.

So the record cannot ship before the row is published, and the button cannot publish before the record ships. That is a deadlock (confirmed by reading the code; see open items).

## What changed

- `lib/catalog-review.ts`: `generateSlug` moved here unchanged from `app/admin/actions.ts`, so the admin button and the new script use one rule. The URL check and the bounded fetch inside `assertCatalogReview` became exported helpers (`primarySourceUrl`, `readPrimarySource`), and `normalize` is exported. The gate behaves as before; its tests pass unchanged.
- `scripts/catalog-admit.mjs` (logic) and `scripts/admit-submissions.mjs` (thin CLI): check a reviewed plan, write review records, write a guarded SQL pack, and verify the readback. Tests in `lib/catalog-admit.test.ts`.
- `server.json`: added `repository` and `icons`, and set `version` to 1.4.0 to match the route's serverInfo. Before, it had neither field and said 1.0.0. `lib/server-manifest.test.ts` fails if they drift again. Checked 2026-11-23: the file passes the official 2025-12-11 schema, both icons serve at the declared sizes, and the live route reports 1.4.0. The public registry still holds 1.0.0 with no repository or icons until someone runs `mcp-publisher publish`; nothing in the repo checks the registry copy yet.

## How the check works

- Slug comes from the admin rule. Bounds match the submit form (name 2 to 100, tagline 10 to 120, description 50 to 2000, enums), plus https only for every URL.
- Control characters and broken Unicode are refused. Other non-ASCII text (curly quotes, accents, CJK) is allowed, as in existing records.
- Absent values become `null`, and absent lists become `[]`. That is what `legalaimcp.catalog_claims()` returns for a stored row with NULL columns and an empty `tags` array, and what every existing record holds. An empty string would hash differently, and the trigger would count an empty `mcp_repo_url` as an MCP claim.
- Blocked slugs and blocked domains are refused. So are duplicate slugs or submission ids in one file, and a slug that already has a different record.
- Each source is fetched with the gate's own helper (HTTPS, no redirects, 2 MB, 12 seconds). The script hashes it with `sourceFingerprint` and checks the quote with the gate's normalization.
- Last, the real `assertCatalogReview` runs against a policy that includes the new record.

## The SQL pack

- `guard.sql` is one read-only SELECT. Every boolean must be true.
- `apply.sql` runs one transaction with lock and statement timeouts. All data sits in one jsonb literal under a random dollar tag, and the tag is regenerated until it does not appear in the data. Non-ASCII characters are written as `\uXXXX` escapes, so every file is pure ASCII.
- The DO block checks every guard again, then for each item inserts the ledger row (claims from `legalaimcp.catalog_claims`), inserts the listing (`submitted`, `published`, `verified` false), and approves the submissions. Rejects only touch rows still `pending`. Any row count that differs from the plan raises, and nothing is saved. Nothing is ever deleted.
- `apply.rollback.sql` is the same file ending in rollback.

## Open items

1. The deadlock above. The admin Approve button cannot publish a new listing today. Not fixed here, by design.
2. `approveSubmission` in `app/admin/actions.ts` does not check `status === 'pending'`. A rejected submission can still be approved when a matching record exists. If the slug is taken, a second approval gets a suffixed slug. Only the review gate stops it, because no record carries that slug.
3. The Supabase connector once turned a typed `\uXXXX` into the real character (see the 2026-11-17 import README). Inside a jsonb literal that gives the same value, so it is harmless. The one case that breaks is a literal backslash typed before `u` in listing text: the JSON would fail to parse and the whole transaction would stop. It fails closed.
4. The generated SQL has not been run or parsed by PostgreSQL. Run `apply.rollback.sql` first.
5. The slug rule drops non-ASCII letters ("Cafe" with an accent becomes `caf`). A name made only of CJK characters gives an empty slug, and the check refuses it.

## Site fixes from the 2026-11-22 offer review

Claude Sonnet 5.5, 2026-11-22. Five fixes, one commit each.

1. A payment can no longer downgrade an editorial pick. Before, the buy button showed on editorial Featured listings and the checkout route took any published listing. The webhook then stamped `featured_until`, and the expiry cron removed Featured 30 days later, so a vendor could pay $69 and lose a placement that had no end date. Now `app/api/stripe/checkout/route.ts` returns 409 when `featured` is true and `featured_until` is null, and `FeatureListingCTA` renders nothing for that state. A small helper, `featuredState`, in `lib/featured-pricing.ts` keeps the two in step. The webhook is unchanged.

2. Paid placement now sorts first. Before, `/servers` ordered by `featured desc, name`, so a paid row sat in the alphabet among the nine editorial rows, and the homepage took six featured rows with no order, so a paid row might not show. Now `/servers`, the category pages, both "best" pages and the homepage six order by `featured desc`, then `featured_until desc` with nulls last (paid, then editorial), then name (`lib/featured-order.ts`). The homepage still re-sorts its six by price tier after the query, as before. The expiry cron now also sets `featured_until` to null when it turns Featured off, so an expired paid row sorts like a plain row. Nothing reads a past `featured_until`; the `payments` rows and `featured_purchased_at` keep the history. Left alone on purpose: `lib/search.ts` (ranking was not to change), the MCP browse query in `app/api/mcp/route.ts` (pricing makes no promise there), and the admin list. A paid listing whose term has ended but whose cron run has not happened yet (up to a day) still sorts first; that gap existed before.

3. Copy. The terms page said Featured placements are paid; it now says paid placements are labeled Sponsored and Featured listings are editorial and not paid. The pricing bullet on search now says a paid placement breaks ties between matches that are equally relevant and equally link-checked, which is what `lib/search.ts` does. The buy box says "Sponsored badge". The success page now gives hello@legalaimcp.com. The footer links to Pricing. A test guards the new wording.

4. Weekly link check. Before, `verify()` threw when the source audit had findings, so the link check below it did not run. Now the audit result is kept, the link check always runs and writes, and the command exits 2 afterward if the audit failed or errored. The audit itself is unchanged. `verify-health.json` keeps its four keys and gains `audit` (ok, checked, findings) and `linkCheck` (ran plus counts) when the audit result is present; `ok` is false and `errorCode` is `SOURCE_AUDIT_FAILED` when the audit failed. `sql()` used `supabase db query --linked --project-ref`, which Supabase CLI 3.x refuses on a hosted project. It now builds its argv with `supabaseArgv` in `scripts/weekly/supabase-argv.mjs`: `--remote=<ref>`, `--yes` for writes, `--read-only` for reads, JSON output. The one caller writes and ignores output.

5. Admin approve and reject now throw `Submission is not pending` unless the row is pending. Before, `approveSubmission` never checked status, and `rejectSubmission` did not load the row. This closes open item 2 above.

Follow-ups, same day.

6. Homepage grid. The homepage re-sorted its six featured rows by price tier after the query, which could bury a paid row. The sort is now `sortHomeFeatured` in `lib/featured-order.ts`: active paid rows first, then the same price-tier order as before. Equal rows keep their incoming order.

7. "Featured badge" wording for buyers. A paid listing shows Sponsored, so these now say Sponsored badge: `app/featured/success/page.tsx` (line 30), `app/pricing/page.tsx` (line 12, the page description, and line 77, the bullet, which no longer says "labeled as sponsored"), and `app/components/FAQ.tsx` (lines 47 and 54). The button and product names are unchanged. Left alone: "Featured labeled when sponsored" in `app/page.tsx` and `app/components/TrustStrip.tsx`, which promise no badge to a payer.

8. Admission duplicate check compares a site key, not the bare host (Claude Sonnet 5.5, 2026-11-22). Before, `scripts/catalog-admit.mjs` compared hosts only, in the plan check, `guard.sql` and the apply block. Seven live listings point at `github.com/<owner>/<repo>`, so every published GitHub listing counted as a conflict for any new repo and `apply.sql` would have raised. Now the key is the host (lower case, no `www.`), and on github.com, gitlab.com, bitbucket.org, codeberg.org, huggingface.co, npmjs.com and pypi.org it is host plus the first two path segments (lower case, trailing `.git` dropped from the second). `siteKey` (JS) and `SQL_SITE_KEY` (SQL text, used in both SQL places) must agree. The plan check now also refuses two admits with the same key, which it did not do before. The payload field `host` keeps its name and carries the key. Unverified: no local PostgreSQL existed, so the SQL was not run against a server.

## Review fixes of 2026-11-23

- `scripts/curate.mjs`: `discover --dry-run` called `finish()`, a const that exists only inside `verify()`, so it threw ReferenceError. That call is gone. The `verify` dry-run branch never called `finish()`, so a dry run with a failed audit exited 0; it now calls it before the return. Test: `lib/curate-exit.test.ts` (source-level, because the script runs on load and has no import seam).
- `app/api/stripe/webhook/route.ts`: the listing update could match an editorial pick (featured, no end date) if an admin made the row editorial after checkout started, and the expiry cron would then remove it 30 days later. The update now also requires `featured = false OR featured_until IS NOT NULL` (a second `.or()`, which PostgREST ANDs with the first). When nothing matches and the row is an editorial pick, the route does not throw (Stripe would retry forever), leaves the listing and `listing_payments.status` alone, logs one `PAID_NO_PLACEMENT` line with the session id and listing id, and returns 200.
- `app/api/stripe/checkout/route.ts`: only editorial picks got the 409. A second purchase inside an active paid term restarted the 30 days and lost the unused days. The gate now uses `featuredState`: editorial keeps its 409, `paid-active` gets a 409 saying to renew after the term ends, and a paid row whose end date has passed still sells. The test that sold a renewal now uses a past end date.
- Late or replayed payment: the webhook wrote `featured=false` with a past end date onto a row when an event arrived more than 30 days after payment. It now skips the listing update in that case and keeps the payment recorded. `app/api/cron/expire-featured/route.ts` filtered on `featured = true`, so a row with a past end date and `featured = false` was never cleaned; the filter is removed, so any row with a past, non-null end date gets `featured=false, featured_until=null`. Editorial rows (end date NULL) are still never touched.
- `app/categories/[slug]/page.tsx`: the order was verified, featured, end date, name, so a paying vendor (new listings are unverified) ranked below every verified plain row, against the pricing page. Category pages now sort by end date first (non-null means a paid term), then verified, featured, name, through `CATEGORY_ORDER` and `orderCategoryPage` in `lib/featured-order.ts`, with `compareCategory` as the tested twin.
- Copy: `app/featured/success/page.tsx` said the placement shows "within a minute"; listing pages cache for 300 seconds (`lib/supabase.ts`), so it now says "within five minutes". `app/components/FeatureListingCTA.tsx` heading "Featured through {date}" is now "Sponsored through {date}", matching the badge.
- `app/api/stripe/webhook/route.ts`: the listing update carried two `.or()` calls, which postgrest-js sends as two `or=` query parameters. PostgREST's own tests never combine two same-key `or=` parameters, so "both are ANDed" was unproven, and our test was a mock. The update now sends one `or=` value, the four-term expansion `and(a,b),...` of (not newer) AND (not editorial), the form its `AndOrParamsSpec.hs` test "can be nested inside the same expression" proves. The mock now evaluates that expression.

Still open: the `PAID_NO_PLACEMENT` case only writes a log line and has no alert yet, so a vendor who paid for an editorial pick is not told and not refunded automatically. Best-of pages (`app/best/[slug]`, `app/best/legal-mcp-servers`) keep verified first, because the pricing page does not promise a boost there. Two checkouts opened before either is paid (two tabs) both charge, and the second payment restarts the 30 days, so the vendor pays twice for about one term. Nothing alerts on that or on `PAID_NO_PLACEMENT` yet; the planned fix is a check in the intake watcher for a completed payment with no matching placement.
